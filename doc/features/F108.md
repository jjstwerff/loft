# @F108 — Lazy store binding — a collection fetches on a miss

## What it is

Bind a collection to a store image and stop loading it. After `store_bind_lazy(parts, "inventory.store")` the collection is a window onto that source: a lookup that **misses** fetches exactly that one entry and keeps it, so the next lookup for the same key is an ordinary resident hit. There is no separate cache to manage — the collection *is* the working set.

The source is whatever `store_load_key` accepts: a local `.store` image, or an `http(s)://` URL served with Range. Binding is per **collection**, not per store, so `persons` and `companies` can come from different sources, and two collections of the same type can bind differently. Binding replaces, and may be done before the collection holds anything.

A lookup never raises, so a bare `null` cannot tell a key that is genuinely absent from a source you could not reach — two different facts, one stable and one not. Three calls separate them:

- `store_lazy_error(c)` — why the last fetch could not reach the source, or `""` when healthy. Reaching the source and not finding the key **clears** it, so a stale error never outlives the truth.
- `store_lazy_faults(c)` — how many fetches could not reach the source. `0` is healthy; after a traversal it answers "how incomplete am I".
- `store_lazy_clear(c)` — acknowledge those faults. It is the only thing that clears them: a later fetch that happens to succeed does not, because a traversal that missed data is still missing it.

## How it aids you

Work with a dataset far larger than memory without writing a loading step, a cache or an eviction policy. Point a collection at the image and use it like any other collection — the entries you touch are the entries you pay for, and the ones you touch twice are free the second time. Because the source can be a URL, the same code queries a dataset sitting on static hosting.

And when the data is incomplete, you find out. A traversal over an unreachable source cannot quietly answer "nothing there" — the fault count is sticky until you acknowledge it, so a partial answer cannot be mistaken for a complete one.

## Example

```loft
struct Part { const id: integer, name: text }

fn main() {
    // Stand in for a dataset you shipped earlier: a plain `.store` image.
    src: hash<Part[id]> = [];
    store_persist_bind(src, "inventory.store");
    src += Part { id: 7, name: "bolt" };
    src += Part { id: 91, name: "washer" };

    // Bind an EMPTY collection to that image. Nothing is loaded yet.
    parts: hash<Part[id]> = [];
    store_bind_lazy(parts, "inventory.store");
    println("resident: {parts.len()}");                 // resident: 0

    p = parts[91];                                      // a miss fetches this one entry
    println("{p.name}, resident: {parts.len()}");       // washer, resident: 1

    q = parts[91];                                      // a hit never leaves the process
    println("same: {p == q}, resident: {parts.len()}"); // same: true, resident: 1

    // A key the source does not have reads as null — and asking why tells a
    // genuine absence apart from a source you could not reach.
    missing = parts[404];
    println("missing: {missing == null}, faults: {store_lazy_faults(parts)}");

    delete("inventory.store");
    delete("inventory.store.dschema");
}
```

The source is **pinned when you bind**, so a traversal sees one consistent world; if the image changes underneath, the fetch is refused and reported through the fault channel rather than silently mixing two versions. Assigning `= []` to a bound collection reclaims what it holds while keeping the binding, which is the blunt way to cap a working set.

The companion feature is `store_load_key` and friends (#93), where you say explicitly which entries to fetch; this is the same machinery driven by the lookups themselves.
