# @F114 — `x[i]` on a library type — `OpIndex` dispatch

## What it is

A type that defines `OpIndex` is subscripted like a built-in collection. `x[i]`
lowers to the ordinary method call `OpIndex(x, i)`, so a matrix, a bitset, a row
or a ring buffer reads as `x[i]` rather than `x.at(i)`.

The index type is whatever the method declares — there is no requirement that a
subscript be an integer, so a row addressed by column NAME takes a `text`.

## How it aids you

This was the last place a library type was visibly not a built-in one: every
other operator already had its `OpCamelCase` method, while a user struct met
*"Indexing a non vector"*. A wrapper type now reads the way its users expect,
and what a miss means is the TYPE's decision rather than the language's.

## Example

```loft
struct Ring {
    data: vector<integer>,
    start: integer,
}

// `x[i]` on a Ring is whatever this says it is.
fn OpIndex(self: Ring, i: integer) -> integer {
    n = len(self.data);
    if n == 0 { return 0; }
    return self.data[(self.start + i) % n] ?? 0;
}

fn main() {
    r = Ring { data: [10, 20, 30], start: 1 };
    println("{r[0]} {r[1]} {r[2]}");    // 20 30 10
}
```

## An interface can require it

```loft
interface Indexable {
    op [] (self: Self, i: integer) -> integer
    fn count(self: Self) -> integer
}

fn total<I: Indexable>(x: I) -> integer {
    s = 0;
    for i in 0..x.count() { s += x[i]; }
    return s;
}
```

Inside a generic only the BOUNDS may be relied on, so an unbounded `<I>` cannot
be subscripted even when every type it is used with defines `OpIndex`.

## One index

The sugar covers a single index. Two subscript spellings a built-in answers are not
available to a library type: the composite `x[a, b]`, which a `hash<Cell[r, c]>` takes,
and the slice `x[a..b]`, which a vector takes. Both stop in the parser with
`Expect token ]` before any `OpIndex` lookup — even though a two-index
`fn OpIndex(self: Mat, r: integer, c: integer)` is accepted and answers correctly when
called by its own name. So a matrix reads as `m.at(r, c)` or `OpIndex(m, r, c)` today
(loft#996).

## `OpIndex` reads

`x[i] = …` is refused, and the message says why: a writing counterpart needs its
own method and a decision about whether `x[i] += 1` may read-modify-write. A type
that must be written through offers a setter — `x.set(i, v)`.
