# @I91 — Editor tooling: language server (LSP), debug adapter (DAP), resolution index

## What it does

Serves loft to an editor over the two protocols editors speak, so a plain text editor
becomes a working loft environment.

The **language server** (LSP) answers questions about the code being displayed and shows
live diagnostics. It re-parses the buffer on every edit with a real stdlib-loaded parser —
the same front end the compiler uses — so what the editor reports is what the compiler
would report, not a second approximation of loft's rules.

The **debug adapter** (DAP) lets you set breakpoints, step, inspect locals and evaluate
expressions in any DAP-aware editor. It is a pure translator rather than a second
debugger: every capability already exists behind the `--rpc` debug engine (@I83), and this
layer adds only the DAP framing and handshake, holding the debuggee in-process.

Underneath the language server, the parser records what each identifier occurrence
actually resolves to as it parses. That index is what lets "what is this symbol?" and
"where else is THIS binding used?" be answered precisely rather than by matching names as
text, which would confuse two different variables that happen to share a name. Recording
is gated behind a flag that is off by default, so ordinary compilation pays nothing.

## Where it lives

`src/bin/loft-lsp.rs` (LSP wire protocol over JSON-RPC / stdio), `src/bin/loft-dap.rs`
(DAP framing over the `--rpc` debug engine), `src/lsp.rs` (the library-side surface that
calls the compiler, so the compiler coupling stays out of the binaries),
`src/resolution.rs` (the parse-time resolution index: position → resolved binding).
