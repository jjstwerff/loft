# @F18 — `const` parameters

## What it is

Put `const` in front of a parameter's type to say this function does not change that value. Every write THROUGH the parameter is a compile error — `p.f = …`, `p[i] = …`, `p += …`, and nested writes under them — so the read-only accessor style is checked rather than promised in a comment.

What it does not yet stop is the value being handed ON. A `const` parameter can still be passed to a function whose own parameter is not `const`, and that callee's write reaches the original record — a plain struct parameter names the caller's value (@F106), so nothing about the second call site says the first one promised anything. Closing that is @PLN40 steps 4–5 in the loft repo; until then, read `const` as *this function does not write it*, not as *nobody downstream writes it*.

## How it aids you

Anyone reading the signature knows this function will not write your data, and if its body ever tries, the compiler says so straight away instead of leaving you to chase a surprise. That is what makes an accessor-style API — `length3(v: const Vec3)`, `mesh_to_floats(m: const Mesh)` — worth reading: the promise is in the type, checked, and costs no copy.

Where the value travels further, follow it: a `const` value handed to a non-`const` parameter is not refused today.

## Example

```loft
struct Account {
    balance: integer
}
fn describe(acct: const Account) -> text {
    "balance is {acct.balance}"
}
fn main() {
    a = Account { balance: 500 };
    println(describe(a));           // balance is 500
    println("still {a.balance}");   // still 500
}
```
