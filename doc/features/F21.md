# @F21 — References `&T` — parameters + write-back bindings

## What it is

Put `&` before a parameter's type to pass a variable by reference. The function then works on your actual variable, so any change it makes stays after the call returns.

`&` is what a **scalar** needs. Without it an `integer`, `float`, `boolean`, `character` or `text` parameter is a copy: the callee's write is gone when the call returns, and the new value has to travel home in the return instead.

A **struct, value struct or collection** parameter is not a copy — it names the caller's own record, so a field or element write through it lands with or without `&`. loft says so itself: a `&` whose only write is a field earns `advice[slow-reference-parameter]`, *"field mutation already propagates to the caller without it"*.

What `&` still buys for those types is **replacing the whole binding**. `s = S { … }` inside the callee reaches the caller only through `&`; without it the new value dies with the call, and nothing at the call site says so.

## How it aids you

Let a function update your data in place — add to a running total, adjust a counter, hand back a parsed value through an out-parameter — without you having to catch a result and assign it back. For a scalar that is the difference between a helper that can update your counter and one that cannot; for a struct or a collection it is the visible way to say the callee may replace the whole thing, not just write into it.

## Example

```loft
fn add_to(x: &integer, amount: integer) {
    x += amount;
}
fn main() {
    total = 10;
    add_to(total, 5);
    add_to(total, 100);
    println("total = {total}");    // total = 115
}
```


## One rule to know

A `&` is an ownership decision, so loft keeps its promise or refuses the program — it will
never quietly hand you a copy instead. Taking a reference into a container and then
**disturbing that container while the reference is still in use** is a compile-time error:
removing from it, writing a key field through the reference, or replacing the container
outright all end the place the reference names.

```loft
c = &v[0];
c.n = 99;      // fine — finished with `c` before `v` changes
v.remove(2);

c = &v[0];
v.remove(2);   // error: cannot remove from `v` while `c` references a place inside it
c.n = 99;
```

Only *liveness* matters, so moving the last use of the reference above the change is the
usual fix. A plain (non-`&`) binding is unaffected: it gets its own copy and is told so.
