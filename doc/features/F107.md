# @F107 — Type reflection — the declared shape of a type, as data

## What it is

`type_of(x)` hands a program the declared shape of a type as ordinary data — its name, the bytes one record occupies, and every field with its own name, type name and byte offset. An enum reports its variants; a vector or keyed collection names its element type. When the name only arrives at runtime — from a config file, a database catalogue, a command line — `type_named("Row")` asks the same question with no value in hand, and answers `null` when this program has no such type.

## How it aids you

A generic serialiser, an ORM mapping or a schema check can be written once, against any type, instead of once per type by hand. The answer is read from the same layout descriptor the store and the browser bridge already use, so reflection cannot drift into a second, disagreeing description of the same memory.

## Example

```loft
struct Row { id: integer, name: text, active: boolean }

fn main() {
    row = Row { id: 7, name: "ada", active: true };

    t = type_of(row);                       // the TYPE of row, not its value
    println("{t.name} — {t.size} bytes");
    for f in t.fields {
        println("  {f.name}: {f.type_name} @{f.position}");
    }

    // The name can also arrive at runtime — from a config file or a catalogue.
    u = type_named("Row");
    if u == null { println("no such type") } else { println("found {u.name}") }
}
```

`type_of` reads its argument for its TYPE and never evaluates it — the contract C's `sizeof` has — so pass a variable, a field or a parameter rather than an expression with a side effect.

Two limits are worth knowing before reaching for it. Reflection is **read-only**: building or mutating a value by field name is a separate and larger question. And it does not work **inside a generic body**, which is parsed once against its type variable, so `type_of(v)` there can only answer with that variable; call it where the concrete type is known.
