# @F98 — `spatial<T[x,y]>` — position-keyed collection for proximity queries

## What it is

`spatial<T[x, y]>` (and `spatial<T[x, y, z]>`) is a keyed collection ordered by **position**. It stores records by their coordinate fields so you can ask what is near a point instead of scanning everything.

## How it aids you

Proximity questions — which mobs are near this one, what is in view, what might collide — stop being a full scan. Ordinary subscript and slice syntax does the asking; there are no special methods to learn.

## Example

```loft
struct Mob { x: integer, y: integer, name: text }

fn main() {
    mobs: spatial<Mob[x, y]> = [];
    mobs += [Mob { x: 10, y: 10, name: "goblin" }];
    mobs += [Mob { x: 12, y: 11, name: "rat" }];
    mobs += [Mob { x: 90, y: 90, name: "dragon" }];

    println("point {mobs[10, 10].name}");        // point goblin

    seen = "";
    for m in mobs[(10, 10)..:2] { seen = seen + m.name + " " }
    println("nearest two: {seen}");              // nearest two: goblin rat
}
```

`xs[x, y]` reads, writes or removes one point. `xs[(x1,y1)..(x2,y2)]` takes a **box** and gives you exactly what is inside it — nothing outside, in the collection's own order; a corner-swapped axis names the same box. `xs[(x,y)..]` and `xs[(x,y)..:n]` walk from a point, and the next section is what they walk. One to three axes; a fourth is refused (*"supports at most 3 coordinate axes, got 4"*).

## The open forms are a TAIL, not a circle

`xs[(x,y)..]` and `xs[(x,y)..:n]` yield only records at or after the query in the collection's own Morton order. They do **not** cover the neighbourhood: a record one code *behind* the query never appears, however close it is, and what you get depends entirely on where the query sits in the curve.

The example above cannot show this, and that is worth knowing before you copy it — its query point is the LOWEST of the three mobs, which is exactly the case where a tail and a true outward walk agree. Move the query to the middle mob and the answer inverts:

```loft
struct Mob { x: integer, y: integer, name: text }

fn main() {
    mobs: spatial<Mob[x, y]> = [];
    mobs += [Mob { x: 10, y: 10, name: "goblin" }];
    mobs += [Mob { x: 12, y: 11, name: "rat" }];
    mobs += [Mob { x: 90, y: 90, name: "dragon" }];

    // From the rat, the goblin is two steps away and the dragon a hundred.
    seen = "";
    for m in mobs[(12, 11)..:2] { seen = seen + m.name + " " }
    println("{seen}");                  // rat dragon — the goblin is behind the query

    // A symmetric box answers every direction.
    near = "";
    for m in mobs[(12 - 5, 11 - 5)..(12 + 5, 11 + 5)] { near = near + m.name + " " }
    println("{near}");                  // goblin rat
}
```

So `..:n` under-delivers, silently, near the end of the curve. Over five records at `(0,0)`, `(5,5)`, `(10,10)`, `(12,11)`, `(20,20)`, a cap of **3** answers:

| query | answered |
|---|---|
| `(0,0)..:3` | 3 |
| `(5,5)..:3` | 3 |
| `(10,10)..:3` | 3 |
| `(12,11)..:3` | 2 |
| `(20,20)..:3` | 1 |
| `(99,99)..:3` | **0** |

Nothing in the result distinguishes "there is nothing near me" from "I am near the end of the curve", and an entity at the far edge of the map asking for the three things nearest it gets nothing at all. `break`ing out of the open form has the same shape — the loop ends early rather than turning round.

**Use a symmetric box for a neighbourhood in every direction** — `xs[(x-r, y-r)..(x+r, y+r)]` — and keep the open forms for what they are: a cheap ordered walk onward from a point, for a sweep you intend to run to the end anyway. loft#1002 tracks giving the language the two-cursor outward walk the engine already implements.
