# @F110 — Diagnostic suggestions — what to write instead, checked by running it

## What it is

A diagnostic tells you something is wrong. loft also tells you **what to write instead**,
and can check that advice by trying it.

Every warning and every advice loft raises carries two things: a **code** — a short name in
brackets, like `warning[redundant-coalesce]` — and one or more **fixes**. The code is stable:
the wording of a message may improve, the code will not, so it is what you search for and
what a tool keys on.

```
$ loft prog.loft
warning[redundant-coalesce]: Redundant null coalescing — 'name' is 'not null', default is never used
  --> prog.loft:6:29

note: 1 diagnostic above suggests what to write instead — re-run with `--explain`
```

`--explain` adds the fixes. Each says what to write, what it needs you to confirm, and the
name of the capability it uses — a word you can search for when you want to know more:

```
  fix  delete the `?? <default>`   [null coalescing · @F2]
```

**`loft fix` runs the advice before offering it.** loft holds the analysis that raised the
diagnostic, so it can apply a suggested rewrite to a private copy of your file, analyse it
again, and see whether the problem actually goes away without causing a new one:

```
$ loft fix prog.loft
prog.loft
  prog.loft:6  delete the `?? <default>`  [verified]
```

`loft fix --apply` writes the ones that pass. It only ever writes a fix whose meaning is
settled by your code alone. Anything resting on a judgement — *"if you no longer need that
variable"* — is reported with the condition and left for you, because nobody is there to
agree to it.

Editors get the same three things: the fixes as quick-fixes, the full list under each
problem, and the code as a link to its documentation.

## How it aids you

The second half of a diagnostic is where most of the learning is. Knowing that a `??` is
redundant teaches you nothing; being shown that the field is already non-null, and that the
idiom has a name you can look up, teaches you the language.

You also get to trust it. A suggestion that has been **tried** is different from one that
was pattern-matched: when loft offers to correct a misspelled name, it has already checked
that the corrected program still compiles. So a rename that is the right spelling but the
wrong call is refused rather than written into your file.

And nothing happens behind your back. Fixes are shown, never applied, until you ask.

## Example

```loft
struct Tile { name: text }

fn main() {
    t = Tile { name: "grass" };
    // `t.name` is never null, so this default can never be used — loft says so,
    // and `--explain` shows the fix: delete it.
    shown = t.name ?? "none";
    println("{shown}");
}
```

Run it with `--explain` to see the fix, or `loft fix --apply` to have it written for you.
