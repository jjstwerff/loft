# @F120 — Lexer library (lib/lexer)

## What it is

The `lexer` library breaks text into TOKENS — the smallest pieces that carry meaning:
numbers, names, operators, quoted strings.

You tell it two things about your language and it handles the rest. `set_tokens` lists the
multi-character operators, so `+=` is scanned as one token instead of a `+` and an `=`.
`set_keywords` lists the reserved words, so `let` comes back as itself and never as an
ordinary name.

Then you read tokens in order with typed readers: `int()` takes the next integer or answers
null, `identifier()` takes the next name, `matches(s)` takes the next token only if it is `s`
and says whether it did, `peek()` looks without taking.

⚠ Not to be confused with **@I57 Lexer**, which is loft's OWN lexer — the compiler stage that
reads your `.loft` files. This is a library your program calls to read text of its own.

## How it aids you

Reading a small language — a config format, a rule file, an expression a user typed — is
mostly tokenising, and tokenising by hand is where the fiddly bugs live: two-character
operators split in half, a keyword swallowed as a variable name, positions that drift so the
error points at the wrong line. Hand it the rules and read the pieces back.

It is also half a foundation: pair it with the `parser` library, or layer your own grammar on
top, and the tokeniser is done.

## Example

```loft
use lexer;

fn main() {
    l = lexer::Lexer { };
    l.set_tokens(["+=", "==", "->"]);        // scanned as ONE token each
    l.set_keywords(["let", "in"]);           // reported as themselves, never as names

    l.parse_string("snippet", "let total += 12");
    println("keyword: {l.matches(\"let\")}");   // keyword: true
    println("name: {l.identifier()}");          // name: total
    println("operator: {l.matches(\"+=\")}");   // operator: true
    println("number: {l.int()}");               // number: 12
}
```
