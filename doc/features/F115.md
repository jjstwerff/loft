# @F115 — `OpDrop` — a type runs code when its scope lets it die

## What it is

A type that defines `OpDrop` runs it when a scope that OWNS one lets the value
die — the shape RAII gives a transaction, a file handle or a C resource.

The rule is one sentence:

> A drop runs exactly where the value's own free runs — the same binding, the
> same scope exit, the same early-exit paths — and never anywhere else.

So it inherits every case that is easy to get wrong by hand: an early `return`, a
`break`, a `return` out of a loop that bypasses the loop epilogue, and
reverse-declaration order within a scope.

## How it aids you

Cleanup stops being something a reader has to verify on every path out of a
function. You write the release once, on the type, and the compiler puts it at
each exit — including the ones you would have forgotten.

## Example

```loft
struct Lease {
    id: integer,
}

fn take(id: integer) -> Lease {
    println("take {id}");
    return Lease { id: id };
}

// Runs when a scope that OWNS a Lease lets it die.
fn OpDrop(self: Lease) { println("release {self.id}"); }

fn hold() {
    a = take(1);
    b = take(2);
    println("working");
}

fn main() {
    hold();
    println("done");
}
```

prints

```
take 1
take 2
working
release 2
release 1
done
```

— reverse declaration order, so nothing outlives what it belongs to.

## What it costs, stated up front

**A drop cannot fail.** It runs at a closing brace with no caller left to tell,
and loft has no runtime errors, so `OpDrop` may not return and one that tries is
refused. Anything whose failure MATTERS stays an explicit call:

```loft
tx.commit()      // may fail; you get the answer
// scope end     // best-effort rollback if not committed; you get nothing
```

That asymmetry is the design, not an oversight.

**A drop reaches the world, not its caller's data.** It receives only `self`, and
a struct field COPIES at construction, so a drop cannot write back into a
caller's collection. Its effect is I/O or a resource it owns — which is exactly
the intended use: a `ROLLBACK` on a connection the transaction holds.

## Other rules worth knowing

- A **returned** value does not drop in the callee; the scope that receives it
  owns it. A **borrowed** argument does not drop in the callee either.
- A binding written inside an `if` block is hoisted to the function scope — that
  is where loft frees it, so that is where it drops. A `for` body IS a scope, so
  a droppable made per iteration drops per iteration.
- A value that was never created never drops.
