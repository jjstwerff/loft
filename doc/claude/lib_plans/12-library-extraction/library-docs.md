## Phase 6.14 — library documentation pipeline (proposed 2026-05-31)

**Trigger.**  Today, every monorepo library (`lib/<pkg>/`)
gets HTML documentation auto-generated by
`cargo run --bin gendoc` → output at `doc/*.html`.  The
generator reads `lib/<pkg>/src/*.loft`, extracts pub
function/type/struct signatures + their doc comments, and
emits a per-library HTML page.

After Phase 5b + 6b ship (Stage B for graphics + net),
those library sources move to chunk repos.  The monorepo's
`gendoc` has nothing to read for the extracted libraries.
Users opening `doc/crypto.html` or `doc/web.html` get stale
content (last generation before extraction) or a missing
page.

This phase ships a replacement: **per-chunk doc generation**
that runs in each chunk's CI, publishes per-version HTML to
gh-pages or `loft-lang.org/libraries/<name>/<ver>/`, and is
linked to from the [library catalog page (Phase 6.15)](closure.md#phase-615--library-catalog-page-generator-proposed-2026-05-31).

**Scope.**

1. **`loft doc <pkg>` CLI** — reads a chunk-repo package
   (`<pkg>/src/*.loft` + `<pkg>/loft.toml`), emits HTML to
   `<pkg>/doc/`.  Mirrors `cargo doc`.  Wraps the existing
   `documentation.rs` parsing logic, extracted into a
   library-callable function.
2. **Chunk-repo CI integration.**  The canonical
   `library-ci.yml` gains a "Generate docs" step after the
   test steps.  Output uploaded as a CI artifact OR pushed
   to a gh-pages branch.
3. **Per-version hosting.**  Options:
   - **(A) gh-pages per chunk repo** — `loft-libs-net` has a
     `gh-pages` branch; each release CI run pushes
     `<pkg>/<ver>/index.html` etc.  URL pattern:
     `https://loft-lang.github.io/loft-libs-net/<pkg>/<ver>/`.
   - **(B) loft-lang.org aggregator** — central site that
     pulls from each chunk's release artifacts on a cron.
     URL pattern: `https://loft-lang.org/libraries/<name>/<ver>/`.
   - **(C) Both** — gh-pages as the canonical hosting; the
     loft-lang.org page is a thin redirect.
   Recommendation: **(A) first, (C) later** — gh-pages is
   zero-infra; the aggregator can grow when there's reason.
4. **Versioned URLs.**  Every published version stays
   accessible at `<name>/<ver>/`.  `<name>/latest/` symlinks
   to the highest active version.
5. **Library catalog integration** — Phase 6.15's catalog
   links each package row to `<name>/latest/`.

**`loft doc <pkg>` — concrete shape:**

```
$ loft doc web
[doc] reading web/src/*.loft (3 files, 47 public symbols)
[doc] writing web/doc/index.html
[doc] writing web/doc/HttpResponse.html
[doc] writing web/doc/WsHandler.html
[doc] 9 pages, 84 KB total
```

Flags:

- `--output <dir>` — override `<pkg>/doc/`.
- `--version <ver>` — annotate generated pages with the
  version (defaults to `loft.toml`'s `version`).
- `--theme <name>` — light / dark; default light.
- `--strict` — fail on missing doc comments for pub
  symbols.  Useful as a CI gate after the library matures.
- `--check` — verify docs are up-to-date without writing
  (for CI gates).

**`library-ci.yml` extension** (canonical template addition):

```yaml
- name: Generate per-package docs
  working-directory: ${{ matrix.package }}
  run: |
    loft doc ${{ matrix.package }}
    # Output at <pkg>/doc/

- name: Upload docs as CI artifact
  uses: actions/upload-artifact@v4
  with:
    name: docs-${{ matrix.package }}-${{ github.sha }}
    path: ${{ matrix.package }}/doc/

# Only run on tagged release commits:
- name: Publish docs to gh-pages
  if: startsWith(github.ref, 'refs/tags/')
  uses: peaceiris/actions-gh-pages@v3
  with:
    github_token: ${{ secrets.GITHUB_TOKEN }}
    publish_dir: ${{ matrix.package }}/doc
    destination_dir: ${{ matrix.package }}/${{ env.PKG_VERSION }}
    keep_files: true  # preserve previous-version dirs
```

**Implementation outline (M, ~3-5 work-days):**

1. **Extract `documentation.rs` into a callable library
   function** — currently `src/gendoc.rs` is a `bin/`
   entry that hardcodes paths.  Refactor: separate the
   "read loft source + emit HTML" core into
   `src/documentation_lib.rs` (callable); keep `bin/gendoc.rs`
   as the monorepo wrapper that calls it for every
   `lib/<pkg>/`.
2. **`loft doc <pkg>` subcommand** in `src/main.rs` — wraps
   the library function.  Reads `<pkg>/loft.toml` for name +
   version; reads `<pkg>/src/*.loft`; emits to
   `<pkg>/doc/`.
3. **Doc-comment extraction.**  Already in
   `documentation.rs`.  Verify it handles per-package
   discovery (which functions are `pub` in this package, vs
   transitive `pub` from deps).  Today's gendoc treats the
   whole monorepo as one universe; per-package needs
   stricter boundaries.
4. **Chunk-repo CI template update** — add the doc-gen +
   gh-pages-publish steps to `library-ci.yml.example`.
   Roll out across `loft-libs-core`, `loft-libs-net`,
   `loft-libs-graphics` via the same omnibus pattern that
   shipped 6.5.
5. **Cross-link generation.**  Each library's docs should
   link to its dependencies' docs (e.g. `game_protocol`'s
   page links `web::HttpResponse` to
   `https://loft-lang.github.io/loft-libs-net/web/0.1.1/HttpResponse.html`).
   Resolution: at doc-gen time, look up each cross-package
   reference in the registry index → format the dep URL.
6. **`latest` symlink updater.**  gh-pages CI step that
   updates `<pkg>/latest/` to point at the newest active
   version (skip yanked-security-critical versions).
7. **Library catalog integration.**  Phase 6.15's
   catalog generator pulls the latest version per package
   from `index.json` and links to `<name>/latest/`.

**Tests** (in `tests/library_docs.rs`):

- `loft doc <pkg>` against a fixture chunk → HTML emitted,
  all pub symbols present.
- `--strict` mode + missing doc comment → exit non-zero.
- Cross-package reference resolves to the right URL.
- Per-package boundary respected (don't emit symbols
  imported via `use other_pkg;`).
- Tagged-release CI run pushes to gh-pages; subsequent
  non-tagged runs don't.

**Open questions:**

1. **Search across packages.**  Should the catalog page
   include a search box that finds symbols across all
   libraries?  Out of scope for 6.14 (per-library docs);
   could be a 6.15 catalog extension or a separate
   web-IDE feature.  Recommendation: defer; build the
   primitives first.
2. **Auto-generated examples.**  Should doc-gen run
   any `///!` example blocks as tests?  Cargo does this.
   Recommendation: yes, but as a separate `loft doc
   --test-examples` flag; not on by default to keep
   normal `loft doc` fast.
3. **Style customisation.**  Default theme — minimal +
   light?  Reuse the existing monorepo gendoc CSS?
   Recommendation: yes — reuse to avoid drift; one CSS
   file shipped with the loft binary.
4. **Versioned URLs as canonical or just sticky.**  When
   a new version ships, do old version URLs stay
   forever, or get garbage-collected at some point?
   Recommendation: stay forever — gh-pages storage is
   free; broken links are user-hostile.

**Why this is M (not S).**  The per-chunk CI rollout is
the same pattern as 6.5 (three chunk repos × one PR each)
but the doc-gen logic itself needs work — today's
`documentation.rs` is monorepo-shaped; chunk-shape
requires per-package boundaries + cross-package link
resolution.  Net effort: ~1 day on the lib refactor, ~1
day on `loft doc` CLI, ~1 day on cross-chunk wiring +
gh-pages CI integration, ~1-2 days on testing + rollout.

**Sequencing relative to Stage B.**  6.14 should land
BEFORE 5b + 6b execute Stage B's library-dir removal —
otherwise users opening the existing `doc/*.html` pages
for extracted libraries hit broken or stale content.
Concrete order:

1. 6.14 ships → `loft doc` works against chunk repos.
2. Each chunk's CI starts emitting docs to gh-pages.
3. Library catalog (6.15) populates with the gh-pages
   links.
4. THEN Stage B (5b + 6b) removes monorepo libraries —
   users redirected to the chunk-repo docs already work.

If 6.14 slips, Stage B should not run for chunks with
significant existing documentation surface (`web`,
`server`, `graphics`) until 6.14 catches up.
