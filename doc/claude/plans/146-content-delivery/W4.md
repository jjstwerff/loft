# @PLN146 W4 — `Fronds`, and the gate that was measuring the wrong binary

The phase gate for **W4**. The plan and its other phases are in [README.md](README.md);
the renderer this completes is [W2.md](W2.md) / [W3.md](W3.md).

## The gate

```sh
corpus/w2.sh                   # now 37 scenes — every Fronds scene joins
corpus/w2.sh --control
```

**37 of 37 scenes, 0 pixels different**, on `--native` and on `--interpret`, and the
control turns all 37 red. `UNBUILT` goes empty: `Petals` stays unbuilt because
[W0](W0.md) measured that no scene in the corpus uses it.

The arithmetic needed no new dependency and no workaround. `draw.py`'s own docstring
says why — *"never random()/hash() (those break reproducible renders)"* — so the field is
a hand-rolled integer hash, and PCG-64 would have moved every jittered frond. The seeded
half was already proved to match Python exactly: the hash including its widest product
(5.47e18, inside `i64` by a hair), the fractal seeds at depth 3, half-to-even rounding,
and `sin`.

## Finding 1 — the phase's blocker was never real

The WIP carried a rewrite of the bowed-frond path (an element-by-element copy of
`f.fpts` into a local, and the `if` spelled as an expression) against a panic
`index out of bounds: the len is 30 but the index is 65535`. That panic is
[loft#1082](https://github.com/loft-lang/loft/issues/1082), fixed and merged in #1084, so
the rewrite had nothing left to do. It came out: the **committed** form renders all 37
scenes pixel-identically, measured with the same gate.

Worth keeping as a lesson rather than a diff: the rewrite *looked* load-bearing, because
with it the corpus was green and without it 1167 pixels moved. Both readings were
artefacts of something else — see finding 2.

## Finding 2 — `--interpret` was not running the interpreter

`w2.sh` ran the corpus on both backends and reported both green. It was running the
**compiled** `drawing` twice.

A `use`d library resolves to its `native-auto/` cdylib **even under `--interpret`** — the
flag picks the backend for the *program*, not for the libraries it loads. So the only
thing `W2_BACKEND=--interpret` changed was `w2.loft` itself, forty lines of driver, while
every pixel was still drawn by compiled code.

It surfaced by accident: a byte-identical **copy** of `drawing/src` rendered 1167 pixels
differently from the original directory. The copy had no `native-auto/` beside it. That is
also what made the WIP rewrite look like a cure — the "before" was a scratch copy and the
"after" was the package.

`LOFT_NO_NATIVE_LIBS=1` is the switch that separates them, and `w2.sh` now sets it
whenever `W2_BACKEND=--interpret`, so the interpret lane measures the interpreter.

## Finding 3 — the interpreter draws a different picture

With the two lanes genuinely separated, the interpreter is **wrong**:
`drawing::smooth_pts` on an outline that mixes smooth (`~`) and corner points answers
`663.464032166672` where the hand-computed value from `draw.py`'s own `_smooth_pts` is
`661.7595` — 1167 wrong pixels on `leaf`, and eight corpus scenes affected. `--native`
answers `661.7595`.

Reduced to fourteen lines with no library, it is
[loft#1085](https://github.com/loft-lang/loft/issues/1085): a struct local bound from an
`if`-expression **call** arm is overwritten by a later allocation in the same iteration.
A caller allocates one `__ref_N` return-buffer placeholder per call site at function
entry; the callee frees it at its own scope exit when it allocated fresh instead of
adopting it; the caller's variable is never reset, so every later iteration frees the same
**stale** store number — and by the fourth iteration that number belongs to a live local.
The next allocation takes the slot straight back.

Three switches agree and are what pin it rather than a story:
`LOFT_NO_SLOT_REUSE=1` clean, `LOFT_STRICT_STORES=1` clean, `LOFT_STORE_TAG=1` silent
(the store-identity gate does not see this free).

The corner tangent in `smooth_pts` is exactly that shape, which is why arc W is what found
it and why no `drawing`-side spelling escapes it — four were measured, all identical.

## Finding 4 — the root is one word of disagreement about `null`

`--native` writes the NULL sentinel for a ref local's null-init
(`let mut var_x: DbRef = DbRef::NULL`); the interpreter's `OpInitRef` **allocates an
empty store**. That is the whole difference. It gives a call-site return buffer
(`__ref_N`) a real store, so the caller keeps it and frees it at scope exit — and the
callee frees it too, because a callee cannot tell a caller-supplied buffer from one the
runtime handed it (`CallRef` for a lambda, the cdylib bridge for a `pub` library
function). The second free releases a slot recycled since, and the next allocation takes
it back.

`LOFT_SENTINEL_INIT_REF=1` takes the native spelling. On it, loft#1085 goes away and
`smooth_pts` answers `661.7595`. It is **opt-in, not the default**, because it also stops
the buffer store being reused in place across a loop, and that reuse was masking a second
leak in tuple destructure (`tests/scripts/1051-tuple-destructure-ownership.loft`,
`Cell×80`) — turning the switch on without closing that would trade a silent wrong answer
for a silent leak.

A narrower fix was measured and rejected: gating the callee's free on whether this
function actually allocates into the buffer (`OpDatabase(v, …)` in its own body) fixes
loft#1085 and keeps loft#688 / loft#1022 green, but it drops the ownership sweep's
backstop for a buffer supplied by the **bridge** — `n3_parity`'s
`shared_bridge_nested_return_no_orphan_leak` defence-in-depth control goes red. The
callee cannot answer "whose buffer is this?" statically, which is why the fix belongs at
the caller's spelling of `null` and not at the free.

## Status

The renderer is complete and the compiled lane is exact. **W4 is not closed**: its own
gate asks for the same pixels on `--interpret` and `--native` alike, and that is an honest
red pending loft#1085. The probe is `probes/1085-ret-buffer-passthrough-free.loft`; run it
with and without `LOFT_SENTINEL_INIT_REF=1`.
