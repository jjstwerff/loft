# @PLN146 F6 — the await that holds the program

The phase gate for **F6**. The declaration it orders is [F5](F5.md); the plan and its
other phases are in [README.md](README.md).

## Two lines, and why they are their own phase

`--html` emits this into the boot sequence, ahead of `loft_start`:

```js
await Promise.all(["DejaVu Sans","LoftProbeFace"].map(
  f => document.fonts.load('16px "' + f + '"').catch(() => {})));
```

Every declared family is awaited, including one the browser already has —
`document.fonts.load` on a resident family resolves at once, and asking makes the three
sources mean the same thing. A family that never arrives is **caught, not thrown**: a
remote font is a third-party dependency, and a blocked CDN should cost a fallback face
rather than a page that does not start.

The fix is two lines. The phase is the test, because on a fast local font the page
resolves whether it waited or not — a gate without a control would report a broken
ordering as a working one.

## The gate is a throttle plus a control

`tests/html_fonts.rs::the_boot_await_holds_the_program_until_a_slow_font_has_arrived`
runs **two pages against one delayed server** (`tests/data/slow_font_server.py`, which
delays font *files* by 800 ms and serves everything else at once):

| page | assertion |
|---|---|
| the emitted await | all three families resolved |
| the same page, await removed | the two families this page BRINGS are unresolved; the resident one still is |

The second is the phase. If it also came back resolved, the first half would be
measuring nothing, so it runs every time rather than once when the harness was written.
The resident family resolving in *both* runs is what proves the control run happened at
all rather than failing early.

## Why it matters more than one frame of the wrong face

The browser bridge caches a font's CSS family per handle. Before [F5](F5.md) fixed
`familyFor`, a `gl_load_font` that ran while the webfont was still loading resolved to a
*generic* and kept that answer for the whole run — so declaring a font and using it
early was worse than not declaring it. With the fix the wrong answer is no longer
permanent, and this await is what keeps the first frames from drawing in the fallback at
all.

## The ordering is asserted as an ordering

`a_declared_font_reaches_the_emitted_page` builds a real `loft --html` page and checks
the await sits **before** the `loft_start` call, not merely that it is present — a block
emitted after the program starts satisfies a substring check and does nothing. It reads
the last occurrence of each: the embedded glue names `loft_start` in its own comments
long before the page boots.
