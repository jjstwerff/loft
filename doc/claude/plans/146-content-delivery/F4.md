# @PLN146 F4 — a page carries the pack it reads

> Phase doc. Plan: [README.md](README.md) · asset doctrine: [ASSETS.md](ASSETS.md).

F4 is `retire build_atlas()`, and it turned out to be three things, not one. The first
was an engine defect: **a `--html` page could not read a store at all**, so the phase's
premise was false before any vehicle work started. That half shipped (`e8953578`) — the
store loader falls back to the page's own filesystem. This doc is the **second** half:
`--html` putting a declared file INTO that filesystem, so a page carries the pack rather
than having one spliced in by hand.

## Why a declaration and not a bundler

[ASSETS.md](ASSETS.md) says not to build the Flash `[Embed]` shape — a flag that sweeps
referenced files into the page — and that stands. The pipeline is a store on a dumb file
server, range-read (F2/F3). What ASSETS.md *does* bless is the exception it names in its
last line: **the bytes a page needs before its first fetch**, and a gallery page that must
be a single self-contained file. That is a declaration, one file at a time, written down
in `loft.toml` where a reader can see the whole list.

## The invariant

> A file declared `[[embed]] path = "P"` is readable inside the page by **exactly** the
> call that reads it on the desktop — same function, same string `"P"`.

Everything below is a re-assertion site for that one sentence:

| Site | What asserts it |
|---|---|
| the declaration | `path` is *the program's* path, not the build box's — so it must be relative and in normal form, and it is resolved from beside the PROGRAM, where loft resolves any path a program passes |
| the emitter | the page key is `/` + `path`, which is what `loft-fs.js` `resolve()` turns `"P"` into under the default cwd `/` |
| `doc/loft-fs.js` | `resolve()` — measured, not assumed (see the probe below) |
| the program | passes `"P"`. Not checkable from here, which is why the other three are strict |

The failure this removes is silent in the same way F5's was: a page that carries the file
under a key nothing asks for answers `store_load` → `false`, the game draws no art, and
nothing on stderr says why.

## The cases, written down before the first was worked

Per CLAUDE.md's matrix rule — the headline of case three survives the work, its specifics
do not.

1. **C1 — a NESTED relative path resolves.** The shipped F4 loader gate only ever proved a
   flat `page.store`, which pins the directory axis. A pack lives at `assets/game.pack`.
   *Control:* the same page with the declaration removed must answer `load=false`.
2. **C2 — the bytes are the desktop's bytes.** Assert a distinctive VALUE and a COUNT, not
   `!= null`: a loader that answered an empty store would pass a "did it load?" check.
3. **C3 — the build refuses drift, before the wasm compile.** Five shapes, each its own
   cell: a missing `source`; an absolute `path`; a `..` escape; a non-normal spelling
   (`./assets/x`); one `path` declared twice with different sources. And the pair that
   must NOT be refused: the same declaration twice, identically — an app and a library it
   uses may name the same file.
4. **C4 — a library's declaration reaches a consumer's page**, with `source` resolved
   against the LIBRARY's root and not the app's. Same route as `[wasm.bridge] host_js`.
5. **C5 — nothing declared, nothing emitted.** A page with no `[[embed]]` must be
   byte-identical to today's, or every existing page grows for a feature it does not use.
6. **C6 — parity end to end:** one source, run on the desktop and in the page, differing
   only in the target, reading the same pack by the same name. C1 + C2 together, and the
   plan's through-line.

## The probe that came first

Before any Rust, the cheapest question: does a nested relative path even reach a base-FS
entry? `doc/loft-fs.js` evaluated in node, `loftBaseFS` seeded by hand:

```
assets/game.pack             -> /assets/game.pack     len=4
deep/a/b/c.store             -> /deep/a/b/c.store     len=1
home/jurjens/build/out.pack  -> /home/jurjens/build/out.pack   len=1
assets/nope.pack (control)   -> ABSENT
```

Two readings. The mechanism holds for nested paths, so the page key is `/` + `path`. And
the third row is the reason an **absolute** `path` is refused: it is carried faithfully,
under a key only a program passing that same build-box path could ask for — which is not
a program that runs anywhere else.

## The declaration

```toml
[[embed]]
path   = "assets/game.pack"   # what the PROGRAM passes; also the key in the page's FS
source = "build/game.pack"    # optional — where the bytes are on the build box,
                              # relative to this loft.toml.  Defaults to `path`.
```

`source` exists because a pack is usually *generated* (a `[[build.asset]]` step writes it
into a build dir) while the program reads it from where it ships. It adds no silent-drift
axis: `path` is the program's path by definition, and a `source` that is not there stops
the build.

## What the cases measured

| Case | Reading |
|---|---|
| **C1 / C2 / C6** | a page declaring `assets/page.store` prints `load=true a=7 b=41` — **the same line the desktop run of that source prints**. Control: the same page with the seed statement stripped, `load=false a=-1 b=-1` |
| **C3** | all four refusals land with **no page written**, and the control (a valid manifest) writes one — so "no page" is a reading rather than a box that never builds |
| **C4** | the consumer's page carries `LIBRARY-OWN-BYTES`, with a same-named `CONSUMER-DECOY-BYTES` sitting in the app's own directory. Without the decoy the test would pass whichever root `source` resolved against |
| **C5** | a program declaring nothing builds a page **byte-identical** to the pre-change binary's, with the wasm base64 masked out |

**Both halves of the gate were proven red.** The one that matters is C1's: emit the file
under its BASE NAME instead of its path, and the page still carries the bytes, the seed
is still there, the control still moves — and the read fails, `load=false`. That is the
defect the invariant is about, and it is precisely what a flat-path gate cannot see. The
refusal half was proven by letting an absolute `path` through.

## Why an absolute `path` is refused rather than carried

A page-absolute path (`/data/tree.obj`) is a legal key — the CHANGELOG's own
`loftBaseFS` example uses one. The problem is that nothing distinguishes it from a
**build-box** absolute path, which is the shape a manifest actually acquires: the author
copies the path their build wrote. Carried faithfully, that key is one only a program
naming this box's directories could ask for, and the page fails silently.

So all absolutes are refused, and the direction is deliberate: accepting more later is
additive and breaks nobody, while tightening later breaks every manifest that took the
loose spelling ([COMPATIBILITY.md](../../COMPATIBILITY.md)). If a page-only program ever
needs a page-absolute key, that is a declaration field, not a relaxation of this one.

## The case the first fixture could not see

The gate's first fixture put the program at the package root, which holds the
program-location axis fixed — [[count-what-a-corpus-holds-fixed]] in one line. Moving it
to the standard `src/<name>.loft` layout broke the invariant immediately:

```
DESKTOP  loft --interpret src/composed.loft   load=false level=-1
PAGE     the page built from that same source  load=true  level=99
```

The page read a file the desktop **cannot open**. loft resolves a path a program passes
relative to the PROGRAM file, so `assets/game.pack` in `src/composed.loft` means
`src/assets/game.pack` — while `source` was defaulting to the file beside the *manifest*.
Two different files, one key, and the page was the only one that worked.

The fix is one line and one sentence: the entry program's declarations resolve against
the program's directory. Then omitting `source` means *the file the desktop run opens*,
which is the parity claim rather than a coincidence of layout. Both now print
`load=true level=99`, through `loft build html` with the pack generated by a
`[[build.asset]]` step. `tests/html_embed.rs::the_embedded_file_is_the_one_the_program_would_open`
plants a decoy beside the manifest so it measures which root resolved, and was proven red
by restoring the manifest root.

**A second defect fell out of the same probe.** `loft build` printed *"asset `pack` ran
but a declared output is missing"* and then `asset `pack` ✓` on the next line. A step that
named its `outputs` promised them; exiting zero without producing them is a failed step,
and the `✓` is what a reader takes away. It now fails, and names the likeliest cause —
a `run` script resolves its own paths against the script, so `scripts/pack.loft` writing
`assets/x` writes `scripts/assets/x`. Guarded by
`build_phase::tests::an_asset_that_does_not_produce_its_declared_output_fails`.

**And a third, filed rather than fixed:** [loft#1075](https://github.com/loft-lang/loft/issues/1075) —
a void function whose body ends in a value expression runs on `--interpret` and fails
rustc on `--native` with a leaked `E0308`. The first asset script hit it
(`fn main() { store_persist_copy(h, "…") }`). `formal/calls.md` (F-Return) does not say
what a void-declared function does with a value tail, so the cure is a design call.

## Two things worth knowing

- **`loft-fs.js` normalises its own base keys.** The constructor runs `resolve()` over
  every entry, so `assets/x` and `/assets/x` land in the same place. The emitter writes
  the leading `/` anyway: the key should say what it means without depending on a
  normalisation happening somewhere else.
- **`store_persist_copy` writes a `.dschema` sidecar**, and a load does not need it —
  measured by deleting it (`load=true a=7 b=41` either way). So one `[[embed]]` per store
  is enough. A page that wants the sidecar carried declares it as a second entry.

## Status

The engine half is done, both ways: a page can read its own filesystem, and `--html`
puts the declared file there. The vehicle — Brick Buster's `build_atlas()` becoming a
packed asset, frames pixel-identical to the baked version — is what remains, and it needs
the `assets` package ([loft-libs-assets#7](https://github.com/loft-lang/loft-libs-assets/pull/7))
to land first.
