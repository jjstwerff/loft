# @PLN146 W3 — the two gradients, and the filter the corpus never names

The phase gate for **W3**. The plan and its other phases are in [README.md](README.md);
the renderer this extends is [W2.md](W2.md).

## The gate

```sh
corpus/w2.sh              # now 29 scenes — `player` joins
corpus/w2.sh --control
```

**29 of 29 scenes, 0 pixels different**, and the control turns all 29 red. `drawing`'s
own suite is 26 tests with a purpose-built three-gradient scene pinned from the oracle;
`graphics` is 103 with nine new Pillow goldens for the bicubic filter.

The corpus increment is exactly **one scene**, and that is not a weak gate — it is the
only scene that *can* test this. Seven scenes use a gradient and six of them also use
`Fronds`, so they belong to W4. `player.draw` carries both kinds: a `dir=` linear `Poly`
and a `radial=`+`at=` `Circle`.

## Finding 1 — the filter is chosen by omission

`draw.py` builds every gradient like this:

```python
im = Image.new("RGB", (100, 100))   # …compute the ramp…
return im.resize((max(1, size[0]), max(1, size[1])))
```

`Image.resize(size)` with **no `resample=` argument is BICUBIC**. Read the call site's
argument list and there is no filter in it at all; read Pillow's default and there is.
So the corpus depends on a specific numeric contract that appears nowhere in the source
it is specified by — the same shape as W0's finding 5 (the 3× supersample), and the
reason to check the *library's* defaults rather than the *call's* arguments when porting.

Measured rather than assumed: `resize(size)` matches BICUBIC on every shape the corpus
produces. (`resize((1,1))` also matches BILINEAR — a coincidence at that size, not a
second default.)

## Finding 2 — the enlargement is the contract, and it rings

The ramp is computed at 100×100 and then blown up to the shape's bounding box, which for
a corpus sprite at 3× is typically a few hundred pixels. Bicubic has **negative lobes**,
so an enlargement overshoots the source's own range: a hard 40→200 step upscaled 4×
spans **28..212** in Pillow.

Computing the ramp directly at final size would be smoother — and wrong. So
`graphics::resize_bicubic` reproduces both steps, and the overshoot is pinned as its own
test rather than only inside a golden, because it is the property a "smooth enough"
resampler quietly loses.

## Finding 3 — the mask only ever holds 0 or 255

`_paint_polygon` stamps the gradient through a polygon mask:

```python
mask = Image.new("L", (w, h), 0)
ImageDraw.Draw(mask).polygon([…], fill=255)
img.paste(grad, (x0p, y0p), mask)
```

`paste` with an `L` mask is documented as a blend, which invites porting the blend
formula. It is not needed: measured over a fractional-coordinate polygon, the mask holds
**exactly `{0, 255}`** — `ImageDraw.polygon` fills spans, it does not anti-alias. So the
paste is a hard **select**, and the gradient's own edge is not smoothed here at all; the
3× supersample is what smooths it, one step later.

The other half of that measurement: an RGB source pasted into an RGBA destination makes
the pasted region **fully opaque** (Pillow converts the source to the destination's mode
first), and leaves everything outside untouched.

## One resampler, two filters

`resize_lanczos` and `resize_bicubic` differ in exactly two things — a support radius and
a kernel — so `graphics` now has one `resample` body taking `(support, filt)` and two thin
public wrappers, rather than two copies of the window arithmetic, the normalisation, the
premultiply and the fixed-point accumulation. Those are one derived fact.

The refactor is behaviour-preserving and was proved so rather than asserted:
`resize_lanczos`'s ten Pillow-derived goldens pass unchanged, and the whole 29-scene
corpus — which resamples every scene through it — is pixel-identical.

## What W4 inherits

`Paint` needed no change: W2 already parsed `grad=` / `radial=` with their `dir=` / `at=`
specs and listed them as deferred, so W3 was two draw paths and a version bump. The same
is true one step further out — `Fronds` parses today, so W4 is the array placement and its
seeded field, not the drawing.

`corpus/w2.sh` is now arc-wide rather than W2-specific: its subset is computed from a
single `UNBUILT` pattern naming the constructs not yet landed, so W4 lands as one edit to
that pattern and the gate goes to 37 of 37.
