# @PLN146 E2 + E3 — audio past "it makes a noise"

The phase gates for **E2** (loop, pan, seek, stop-all) and **E3** (`audio_bus`).
The plan and its other phases are in [README.md](README.md); `E1` is the bridge these
extend.

## The gates

```sh
cargo test --test audio_bridge --release          # the browser half of E2
cd loft-libs-graphics/graphics/native && cargo test   # the native half
cd loft-libs-game/audio_bus && loft --tests tests     # E3, both backends
```

**E2**: the browser probe renders through an `OfflineAudioContext` and measures SAMPLES,
each check with the control that fails if the flag is dropped — a looping clip fills the
tail of a one-second render and a non-looping one does not; pan -1 is silent on the right
and pan 1 on the left; `set_pan` moves a sound already playing; a clip whose first 0.15 s
are silence is audible AT ONCE when started (or sought) past them and silent when not;
two looping sounds go quiet on `stop_all`. Ten Rust unit tests carry the native half.

**E3**: twelve tests, green on both backends, none of which plays a sound.

## Finding 1 — the E1 gate was passing on a page that never finished

`tools/html_render_check.mjs` fails a page on a `console.error`. So a probe that runs
past `--wait-ms` reports nothing, and **saying nothing reads as green**. Measured: with
the `looping` flag deliberately dropped in the bridge, the test stayed green — the page
was still working through its renders when the harness stopped watching.

Two changes. The probe **polls** for each decode instead of sleeping 400 ms a dozen
times over (a zero-volume play answers -1 until the buffer lands, which is the readiness
question without needing a new import). And the test passes `--assert` on the probe's own
completion text, so a page that has not reached its last line fails. With both, the same
control turns it red — and so do controls on the start offset and on the pan.

The shape is worth naming because the harness has other users: **a gate whose failure
signal is "an error appeared" is vacuous unless something also asserts the run
COMPLETED.**

## Finding 2 — two targets, one contract, and the browser has the specification

Where the two halves could differ, the native side takes Web Audio's answer:

- **Pan.** rodio has no pan on a `Sink` at all, so this is new code either way — and
  `StereoPannerNode` is *specified*, including the part that is easy to miss: a MONO
  input gets an equal-power pair of gains, a STEREO input keeps its image and is pushed
  toward one side. Panning a stereo clip with the mono law loses the far channel instead
  of narrowing the image.
- **`start` under `loop`.** `AudioBufferSourceNode.start(when, offset)` with `loop = true`
  and no `loopStart` skips into the FIRST pass and then repeats the buffer whole. That is
  why a late-starting loop on the native side is two appended sources rather than an
  offset baked into the repeat.
- **A sink id is never reused.** The browser bridge already said so in a comment; the
  native side reused slot numbers, so a `stop` on a finished sound stopped whatever had
  taken its place. Ids now carry the generation of the slot they name.

## Finding 3 — CI has no audio device, so the tests cannot need one

`rodio::OutputStream::try_default()` fails on the runner, and everything past it answers
-1. A test that opens a stream therefore gates nothing.

Both halves are built so the CLAIMS can be measured without one. On the native side the
pan law is checked as numbers, and the source chain is pulled sample by sample off a ramp
whose values say where in the clip they came from — a loop reads `1,2,3,4,1,2,…`, a late
start reads `3,4` and then repeats from `1`. In `audio_bus`, `attach` puts a handle the
caller already holds onto a bus, which is the seam the whole suite runs through.

## Finding 4 — a duck is not a multiplication

`audio_bus`' one real invariant. A game ducks the music under speech a thousand times an
hour; restoring by dividing the ducked gain back out accumulates a drift that ends with
the music a few percent from where the player put it and nothing saying where it went.

So a duck REMEMBERS the level it replaced and puts that number back — nothing is computed
on the way home. The test runs a thousand duck/unduck pairs on `0.35` (no exact binary
form) and asserts the same bits come out; a restore that multiplies by `1.0000000001`
reddens three tests. A duck inside a duck keeps the ORIGINAL level, because the second
speaker starting must not turn the first one's restore into a guess.

## What is deliberately not here

**Spatial audio** — a sound at a world position, with a listener. `audio_bus::pan` moves
one voice and the caller supplies the number, because placing a sound needs a world and a
listener and a mixer has neither. [LAVITION.md](../../LAVITION.md) § `audio_bus` carries
it as the next slice.

**A DSP graph** — no filters, no sends, no compressor. A bus is a multiplication; past
that is a sound engine, which a 2-D game does not need.
