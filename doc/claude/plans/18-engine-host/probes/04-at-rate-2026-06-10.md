# Phase 04 — state-sync at rate: the @PLAN50 targets measured on the kernel (2026-06-10)

Setup: `probe_server_kernel.loft` (kernel listener, 30 Hz, sight 80 m,
`sync_class_keyed(2)` poses / `sync_class(5)` echo replies), web tier =
`probe.loft` (WS clients on the 6×N grid), native seat =
`probe_client_kernel.loft` (the connector role, plane at the grid center,
echo every 207 ms).  Loopback; interpreted meaning end to end.

Published targets ([@PLAN50 00a](../../future/50-bumper-airplanes/00a-network-probe.md)):
≥ 28 Hz per client both directions; e2e p99 < 100 ms (fail > 150 ms); zero
event drops in a 30 s run; ship tier = 30 clients @ 30 Hz.

## M1 — the tier ladder (web/WS clients)

| Tier | Pose rate / in-sight peer (full-sight client) | Server hold p50 (t5−t1) | hold max |
|---|---|---|---|
| 3 | 30.8 Hz | 14.5 ms | 31.2 ms |
| 12 | 30.8 Hz | 17.3 ms | 33.8 ms |
| 20 | 30.8 Hz | 18.8 ms | 33.3 ms |
| **30 (+1 native)** | **30.3 Hz** | 24.3 ms | 36.4 ms |

Every tier ≥ the 28 Hz threshold; hold stays tick-bounded through the ship
tier (the slow climb 14.5 → 24.3 ms is queue position under the 31-plane
fan-out, not degradation — max never exceeds ~tick+3 ms).  Web-client
turn-around p50/p95 = 60.8/72.5 ms — under the 100 ms target with the known
~40 ms WS-probe-harness term included.  EXIT counts cluster exactly along
the grid's symmetry classes (8×11, 4×7, 4×6, 4×15, …) — deterministic
event delivery; the phase-00 lib/server EXIT-starvation pathology does not
exist on the kernel (the classes are separate queues by construction).

## M2 — the native seat (the connector, UDP fast path)

- `udp=true` (auto-negotiated; zero transport code in either program).
- Fresh poses **29.8/tick** for 30 visible peers — the conflated equivalent
  of ≥ 28 Hz (each tick drains the newest value per plane).
- **e2e turn-around (t6−t0, one clock) p50 = 33.34 ms, p95 = 33.42 ms — one
  tick, almost exactly, with ~0.1 ms jitter.**  3× inside the 100 ms target.

**Finding: tick-grid quantization.**  With two fixed 30 Hz grids (server
tick + client drain tick), e2e latency is **constant**: the wait for the
server's next tick plus the wait for the client's next drain sums to a fixed
k×T regardless of send phase (33.34 ms ≈ k=1 here).  The UDP transport leg
is µs-invisible inside it.  Consequence for the latency budget: at LAN
RTTs, **e2e is set by the tick period alone** — the levers are T itself and
phase alignment, not the wire.

**Finding: cadence phase-lock.**  The first run used a 200 ms echo cadence —
exactly 6 ticks — which froze the echo at one fixed phase: hold pinned at a
FULL tick (33.3 ms, p50 == p95), e2e at 2×T.  An input cadence that divides
the tick period sits at one fixed (possibly worst-case) phase offset.
De-aliased with a co-prime 207 ms cadence.  Real-game relevance: clients
sending input at tick cadence will sit at a fixed phase — measuring (and
eventually nudging) that offset is a cheap latency lever the stamp chain
exposes.

## M3 — the loss axis (LOFT_UDP_DROP_NTH=4 → 25% injected datagram loss)

- Poses **22.5/tick = exactly 75%** — degradation is linear in loss.
- Survivor latency **unchanged** (p50 = 33.34 ms, p95 = 33.40 ms).
- No stall, no recovery machinery, stale-discard intact — the sync class's
  graceful-degradation claim, measured.  (Lost echo replies simply reduce
  the sample count: latest-value semantics.)

`LOFT_UDP_DROP_NTH` is a measurement-only instrument in the connector pump
(deterministic every-Nth drop; loopback has no real loss).

## Verdict

**The ship tier passes on the kernel**: 30 clients × 30 Hz both directions,
interpreted meaning, with the native seat at one-tick e2e and the web seats
within every published threshold.  Remaining phase-04 scope that is
consumer-side meaning, not kernel work: **priority keyframes** (a bounce
promoting a pose sample to a must-deliver event) — lands with
bumper-airplanes phase 0, whose forecast tests are the first caller.
