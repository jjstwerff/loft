# Phase 00(b) — pump-rate baseline, 2026-06-10

**Setup:** `engine-host` branch tip (= main post-#308 + @PLN18 docs); release
build; `server`/`web` 0.1.1 resolved from the registry cache
(`~/.loft/registry/`, auto-install path — the registry consumption path works);
`probe_server.loft` (30 Hz tick) + `probe.loft`, 12 clients, 10 s drain, local
loopback.

**Result — the ~12 Hz finding REPRODUCES:**

- POSE received per client over 10 s: **238–401** (mean ≈ 343) vs the probe's
  stated full-sight expectation ≈ 900 → **~27–45% of target rate** — i.e. an
  effective per-peer rate in the ~8–13 Hz band against the 30 Hz design target.
  Consistent with the @PLAN50 MVP's observed ~12 Hz.
- Spread is large (238 vs 401 across same-grid clients) → the bottleneck is not
  a uniform cap; suspect per-connection send queuing in the pump's broadcast
  path (to be split by the (c) stamp chain: tick wait vs send-queue vs drain).

**New finding — EXIT delivery is lossy under load:** after moving client 0 far,
4 of 11 clients (4, 5, 10, 11) received **0** EXIT events (expected exactly 1
each). EXIT is an *event-class* message over WS (reliable transport!), so the
loss is in the pump or the server's visibility bookkeeping, not the wire —
i.e. today's stack drops must-deliver events under pose load. This is exactly
the class-separation argument: state-sync flooding must never starve events.
Track as a phase-00 investigation item; the kernel's per-class queues (01) are
the structural fix, but the pump-level cause should be named first.

**Next:** (1) instrument the t0–t7 stamp chain into probe_server/probe to split
the latency budget; (2) localize the pump bottleneck in `lib/server`'s native
half (the 12→30 Hz mechanics fix); (3) re-run at 20/30 clients per the 00a
spec's tiers.

## Root cause NAILED (same day, by measurement)

**The pump's empty-sweep cost is `N × ~21 ms`** — measured directly with
[`pump_sweep_probe.loft`](../../../../tools/audience-demo-50/pump_sweep_probe.loft)
at 12 quiescent clients: **min 251.8 ms / mean 252.5 ms / max 255.0 ms per empty
`poll_event` sweep** (tightly clustered = deterministic mechanism, not noise).

Mechanism (in `lib/server`'s native half, `lib.rs`): each connected client's stream
uses a **20 ms blocking read timeout** (`set_read_timeout(20ms)`, the "short-timeout
polling" design), and `n_ws_next_event` scans clients **in order, one event per
call, restarting at client 0**. An idle client therefore costs a full 20-ish ms
block per scan, and every drain-to-empty pass ends with one full all-idle sweep:

- 12 clients → ~252 ms sweep → the server's 30 Hz tick collapses (observed
  ~10.5 Hz effective with probe traffic mixing in; one heartbeat at tick=150 in
  ~14 s).
- 30 clients → ~630 ms sweeps → the @PLAN50 "12 Hz" finding and worse.
- The in-order restart-at-0 scan also explains the per-cid rate bias
  (early-scanned clients drain first).

**Model-falsification note (the matrix at work):** the first hypothesis (timeout
burn ∝ N explaining the *ratio*) was falsified by the 3-vs-12 tier matrix — the
delivered ratio was ~constant because the *tick rate* is what collapses, and pose
emission is per-tick. The sweep probe then measured the mechanism directly.
Measurement contamination caught on the way: sweeps timed during the connection
ramp absorb blocking upgrade-header reads (max 254 ms spikes at clients=1) — the
probe now gates on 2 s of quiescence.

**The fix direction (mechanics, one site):** non-blocking poll — `peek()` the
2-byte WS header with the stream non-blocking (`WouldBlock` → `NoData` in µs;
≥1 byte → fall through to the existing blocking frame read, whose remainder is
already in flight). Empty sweep cost drops from `N × 21 ms` to `N × syscall-µs`.
Apply in `loft-libs-net`'s server pump via the local-shadow loop, verify with this
probe (expect sweep ≈ tens of µs at 12 clients), then re-run the pose tiers
(expect ~900/client) and re-check the EXIT-loss finding under full-rate ticks.

**Side finding (filed #310):** warm startup-cache loads drop `pending_native_libs`
→ every cached run of a native-lib program panics "native function not loaded";
`LOFT_NO_CACHE=1` is the verified workaround (used for all measurements above).
The first 12-client "baseline" additionally ran from a *cached native binary*
whose child process survived a parent kill (`/tmp/loft_native_bin_<pid>`) — both
stale-artifact traps now named.

## Fix VERIFIED (same day) — and the EXIT finding corrected

The peek-based fast-idle poll (patched in a local `loft-libs-net` shadow,
verified through `--lib` shadowing — the edit-a-dependency loop, working):

| Metric | Broken pump | Patched pump |
|---|---|---|
| Empty sweep @ 12 clients | **252,514 µs** | **17 µs** (min 15 / max 30) — ~15,000× |
| Server tick rate | ~10.5 Hz | **30 Hz** (tick=300 at 10 s, both tiers) |
| Poses/client, tier 3 | 312 | **618 — exactly at rate** (2 visible peers × 30 Hz × 10 s, uniform 618/618/618) |
| Poses/client, tier 12 | 238–428 (scan-order bias) | **2198–3432 — at rate**, spread now tracks *visible-peer count by grid position*, not scan order |

**The "EXIT loss" finding is RETRACTED — it was a probe-assertion artifact.** The
same 4 clients "missed" EXITs at both tick rates because they sit ≥ 80 m from
client 0 in the spawn grid ((80,0) d=80, (100,0) d=100, (80,20) d=82.5,
(100,20) d=102 vs sight 80): client 0 was **never in their sight**, so no EXIT
was ever due. EXIT signaling is correct; `probe.loft`'s expectation should be
range-aware. (The earlier "events starve under pose load" interpretation is
withdrawn; the per-class queue design stands on its latency/HOL grounds, not on
this datapoint.)

**Patch (one site, `loft-libs-net/server/native/src/lib.rs` `poll_one_client`):**
non-blocking `peek()` of the 2-byte WS header per scan — `WouldBlock` → `NoData`
in µs; bytes pending → the existing blocking frame read (the 20 ms timeout still
bounds a torn frame); `Ok(0)` → orderly close. Status: verified locally via the
shadow; **not yet pushed/PR'd to loft-libs-net** (and the local clone carries an
unrelated unpushed commit, `454813f`, to keep out of the change).
