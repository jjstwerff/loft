# TTT v3.5 — loft-WASM browser client (design)

The `tictactoe_server_v3.loft` shipped today serves an interactive
HTML+JS board.  v3.5 swaps that JS client for a **loft client
running in the browser via the loft interpreter WASM** — closing
the loop the v3 plan envisioned ("the loft client is a real loft
program").

## Status

**Spike landed 2026-05-11.**  The spike confirmed branch (a) of
Piece 2 (lib/web needs baking in) and surfaced one new blocker:
the synchronous `compile_and_run` entry point can't drive a real
WebSocket because the loft program never yields back to the JS
event loop.  Pieces 1 + 2 (lib/web baked in, host_ws_* +
n_ws_* + JS bridge) are SHIPPED.  Piece 3 (bootstrap HTML) and
the cargo harness wait on the frame-yield resume loop being
wired into the bootstrap (see § Spike findings below).

## Goal

A real browser opens `http://localhost:7878/`, the page loads
the loft interpreter WASM (already shipped in `doc/pkg/`), the
interpreter compiles + runs `client.loft` (a real loft source
file the server delivers), and that loft program connects to
`/ws` and plays tic-tac-toe — all without a separate JS client,
without a build step at server startup, and on the same single
loft binary the v3 server already is.

This proves loft can deliver loft-source clients to browsers —
the deployment story plan-32 has been pointing toward since v1
("the laptop client distribution mechanism" the user called out).

## Spike findings (2026-05-11)

Three concrete results from the empirical spike:

**1. lib/web is NOT in the wasm bundle today** (branch a confirmed).
A `use web; web::ws_handler(…);` program returned `Library 'web'
not found` from `compile_and_run`.  Fix: bake
`lib/web/src/web.loft` into `BUNDLED_LIB_FILES` in `src/wasm.rs`.
**Shipped** — see commit landing this design update.

**2. The native fns lib/web declares need static registration.**
After baking the loft source, the parser succeeded but the
interpreter panicked at `src/compile.rs:205` with
`native function not loaded — call extensions::load_all() first`
on the first `n_ws_*` call.  Fix: add a wasm-feature-gated
`WEB_FUNCTIONS_WASM` table to `src/native.rs` (mirrors the
`fn n_now() ...` wasm/non-wasm split pattern) and register entries
for n_ws_connect / send / send_binary / recv / message / opcode /
close (real impls routing to JS via `crate::wasm::host_ws_*`),
plus stubs for n_http_* / n_pack_* / n_byte_at / n_sleep_ms (the
v3.5 minimal client doesn't need them; later milestones can swap
in real impls).  **Shipped.**

**3. The synchronous `compile_and_run` can't drive an async
WebSocket.**  After rebuilding with the bridges in place, a loft
client that does `web::ws_handler("ws://localhost:18401/ws"); …
h.send("click:0,0"); …` returned the handler id (slot 0) and then
**never advanced** — neither the WS open event nor the inbound
message ever fires while the WASM call is on-stack.  This is the
fundamental sync/async constraint of the WASM execution model:
the loft interpreter runs synchronously inside one JS callstack;
the JS event loop (which delivers `socket.onopen`,
`socket.onmessage`) doesn't get a turn until the WASM call
returns.  `web::sleep_ms(N)` is a busy-wait equivalent at the JS
level — it blocks the JS thread for N ms but never yields.

**Fix: use the `compile_and_start` + `resume_frame` pair instead
of `compile_and_run`.**  Plan-31's HTML-export path already uses
this for graphics frame loops (see `src/main.rs::--html`'s
`AsyncifyCtrl` shape).  The browser-side bootstrap calls
`compile_and_start(...)`, which runs until the loft program calls
`yield_to_host()` (or hits an asyncify-instrumented point), then
returns to JS.  JS's event loop runs (deliver WS events, etc.),
then `resume_frame()` re-enters the loft program from where it
yielded.  This is a known-good pattern; the v3.5 client just has
to use it.

**The full unification of this lives in
[`plans/future/23-event-loop/` § Design principle — four-target
async portability](../../future/23-event-loop/README.md#design-principle--four-target-async-portability).**
That section defines `yield_to_host()` as a single builtin
whose impl differs per target (no-op on interp/native, asyncify
yield on WASM-direct, YIELD_REQUESTED-flag on WASM-interpreter),
plus an `iterator<Event>` API so loft client code reads
identically in all 4 targets.  YIELD.2 (the WASM-interpreter
yield primitive) is the specific phase that unblocks v3.5.

The bootstrap HTML thus has TWO call shapes to choose from:

```js
// Wrong for WS clients — synchronous, no event-loop turns:
const result = JSON.parse(compile_and_run([...]));

// Right — yield + resume in a per-frame loop:
const handle = compile_and_start([...]);
function step() {
  if (!resume_frame(handle)) return;       // false → done
  requestAnimationFrame(step);
}
step();
```

**Effort change:** Piece 3 (bootstrap HTML) grows from S to S/M
because of the resume loop.  Piece 4 (`tictactoe_client_v3_5.loft`)
needs explicit `yield_to_host()` calls between WS poll iterations
(or relies on asyncify-imports auto-instrumenting `host_ws_recv`
to yield).  Piece 5 (cargo harness via Node) needs the same
resume loop.

## Reuse audit — what's already shipped

The GitHub Pages playground (`doc/playground.html`) already runs
arbitrary loft programs in a browser via the same wasm-pack
artifact bundle.  v3.5 reuses 100 % of it:

| Artifact | Size | Source | What it does |
|---|---|---|---|
| `doc/pkg/loft_bg.wasm` | 1.96 MB | `make wasm` (`wasm-pack build --target web --features wasm --no-default-features`) | The Rust→WASM **loft interpreter** — the same code path `cargo run --bin loft` runs natively, compiled to WASM |
| `doc/pkg/loft.js` | 16 KB | wasm-bindgen | JS glue.  Exports `compile_and_run(files_json) → JSON-result`, plus `compile_and_start` + `resume_frame` (frame-yield path) and `worker_entry` (for parallel workers — out of scope for v3.5) |
| `doc/loft-rt.js` | ~600 lines | combines `tests/wasm/virt-fs.mjs` + `tests/wasm/host.mjs` | Host bridge — `createHost()` provides `window.loftHost.fs_*` (full virtual filesystem), random / time / log / storage stubs |
| `doc/playground.html` | reference impl | hand-written | Working "fetch source → compile_and_run → render output" template; v3.5 uses a different UI shape (a board, not an editor) but the run-loop is identical |

The wasm-pack build is gated by the `wasm` Cargo feature.  Today
this feature **excludes** the default-feature crates (notably
`threading` and lib/server's native — those don't make sense in a
browser anyway), so the WASM bundle is the loft interpreter +
default stdlib only.

## Architecture

```
                  ┌──────────────────────────────────────┐
                  │         tictactoe_server_v3          │
                  │           (loft interpreter)         │
                  ├──────────────────────────────────────┤
                  │ HTTP routes (existing + new)         │
                  │  GET /              → INDEX_HTML     │
                  │  GET /pkg/loft.js   → file read      │  ← new
                  │  GET /pkg/loft_bg.wasm → file read   │  ← new
                  │  GET /loft-rt.js    → file read      │  ← new
                  │  GET /client.loft   → file read      │  ← new
                  │  GET /ws            → WebSocket      │
                  └────────────┬─────────────────────────┘
                               │ HTTP/WS
                               ▼
                  ┌──────────────────────────────────────┐
                  │              browser                 │
                  ├──────────────────────────────────────┤
                  │  index.html (small bootstrap)        │
                  │   ↓ import loft.js + loft-rt.js      │
                  │   ↓ fetch client.loft                │
                  │   ↓ createHost(); window.loftHost=h  │
                  │   ↓ compile_and_run([{name,content}])│
                  │                                       │
                  │  ┌─────────────────────────────────┐ │
                  │  │ loft interpreter WASM runs       │ │
                  │  │ client.loft, calls:              │ │
                  │  │   web::ws_handler("ws://…/ws")   │ │
                  │  │     │                             │ │
                  │  │     ▼ via host_ws_*              │ │
                  │  │   loft-rt.js's WS bridge          │ │ ← new
                  │  │     │                             │ │
                  │  │     ▼ wraps                       │ │
                  │  │   browser's WebSocket             │ │
                  │  └─────────────────────────────────┘ │
                  └──────────────────────────────────────┘
```

Three trust / API boundaries crossed:

1. **HTTP** — server delivers four asset files + the loft client
   source.  Same routing layer v3 already has; just four more
   path arms.
2. **wasm-bindgen** — `loft.js::compile_and_run` is the entry
   point.  The browser passes loft source in, gets execution
   results out.  Already shipped.
3. **`loft-rt.js` host imports** — every native fn the loft
   stdlib needs (file I/O, random, time, …) is implemented in JS
   and registered on `window.loftHost`.  The Rust side calls
   them as wasm-bindgen imports.  v3.5 adds the WebSocket family
   to this set.

## What v3.5 has to build — four small pieces

### Piece 1 — `ws_*` host bridge in `loft-rt.js`

The wasm side imports already exist in
`lib/web/native/src/ws_client.rs::wasm_impl` (lines 553-559):

```rust
unsafe extern "C" {
    fn host_ws_connect(url_ptr: *const u8, url_len: usize) -> i32;
    fn host_ws_send(handle: i32, msg_ptr: *const u8, msg_len: usize) -> i32;
    fn host_ws_recv(handle: i32, out_buf_ptr: *mut u8, out_buf_cap: usize) -> i32;
    fn host_ws_close(handle: i32);
}
```

These are dangling waiting for the JS host to register them.
Add to `loft-rt.js::createHost`:

```js
const wsConns = [];   // index → { socket, inbox: [Uint8Array] }
host.ws_connect = (url) => {
  const id = wsConns.length;
  const inbox = [];
  let socket;
  try {
    socket = new WebSocket(url);
    socket.binaryType = 'arraybuffer';
    socket.addEventListener('message', (ev) => {
      const data = typeof ev.data === 'string'
        ? new TextEncoder().encode(ev.data)
        : new Uint8Array(ev.data);
      inbox.push(data);
    });
    // Register; failures (bad URL) throw synchronously
  } catch (e) {
    return -1;
  }
  wsConns.push({ socket, inbox, ready: false });
  socket.addEventListener('open',  () => { wsConns[id].ready = true;  });
  socket.addEventListener('close', () => { wsConns[id].ready = false; });
  return id;
};
host.ws_send = (id, msg) => {
  const c = wsConns[id]; if (!c || !c.ready) return 0;
  try { c.socket.send(msg); return 1; } catch { return 0; }
};
host.ws_recv = (id, outBuf, cap) => {
  const c = wsConns[id]; if (!c) return -1;
  if (c.inbox.length === 0) return 0;
  const next = c.inbox.shift();
  const n = Math.min(next.length, cap);
  outBuf.set(next.subarray(0, n));
  return n;
};
host.ws_close = (id) => {
  const c = wsConns[id]; if (!c) return;
  try { c.socket.close(); } catch {}
};
```

**Open detail:** binary vs text frames.  The wasm-side
`host_ws_send(msg_ptr, len)` doesn't carry a "binary or text"
flag, but lib/web's native side has `send` (text) and
`send_binary` (binary) — distinct C-ABI symbols.  The wasm-impl
today only declares `host_ws_send` and binary falls back to text
(stub).  v3.5 needs `host_ws_send_binary` too, with the same
shape; loft-rt.js's bridge can branch on a separate import.
Same for `host_ws_opcode` → `host.ws_opcode = (id) => …` so
loft-rt.js exposes the 0x01 / 0x02 distinction the receiver
needs.

Effort: **S** (~80 lines of JS).

### Piece 2 — lib/web availability in the wasm-pack interpreter

This is the **30-min spike question.**  Today's
`make wasm` builds:

```
wasm-pack build --target web --out-dir doc/pkg --release \
  -- --features wasm --no-default-features
```

The `wasm` feature gate doesn't include lib/server / lib/web;
those are external cdylibs that can't load in the browser
anyway.  So when a loft program does `use web; web::ws_handler(…);`
through `compile_and_run`, the parser would either:

- (a) **Fail at parse time** with `Library 'web' not found` —
  then v3.5 needs to compile lib/web's loft source into the
  wasm-pack bundle (e.g., via a build.rs that embeds the
  `lib/web/src/web.loft` text + the wasm_impl-side native fn
  registrations).
- (b) **Resolve fine** (the wasm-pack build already includes
  lib/web's loft source via some path I haven't audited) —
  then v3.5 just needs the host imports from Piece 1.

The 30-min spike: write a tiny loft program

```loft
use web;
fn main() {
  h = web::ws_handler("ws://localhost/ignored");
  println("got id={h.id}");
}
```

and try running it through the existing playground.  The error
(or success) tells us which branch v3.5 is in.

If (a): effort jumps from S to **M** (compile lib/web's loft
source into the wasm bundle as a baked-in library — the same
treatment the default stdlib gets today).

If (b): no extra work beyond Piece 1.

### Piece 3 — bootstrap HTML page

A minimal page (~100 lines) modelled on `doc/playground.html`:

```html
<!doctype html>
<html>
<head><title>tic-tac-toe (loft v3.5)</title></head>
<body>
  <h1>tic-tac-toe (loft v3.5)</h1>
  <div id="status">loading interpreter…</div>
  <div id="board"></div>
  <script type="module">
    import init, { compile_and_run } from './pkg/loft.js';
    import { createHost } from './loft-rt.js';
    const { host } = createHost();
    window.loftHost = host;
    await init();
    const src = await fetch('/client.loft').then(r => r.text());
    const result = JSON.parse(compile_and_run(JSON.stringify(
      [{ name: 'main.loft', content: src }]
    )));
    document.getElementById('status').textContent =
      result.success ? 'running' : 'compile error: ' + (result.diagnostics?.[0] || '?');
  </script>
</body>
</html>
```

The board UI (the cells, click handlers, place/gameover
rendering) lives **inside `client.loft`** — it calls the loft
DOM API.  See Piece 4 for what that loft client looks like.

Effort: **S**.

### Piece 4 — `client.loft` (the loft browser client)

The loft program the browser interpreter runs.  Two open
sub-questions:

**(4a) DOM access from loft.**  The browser-side board needs
to render cells and respond to clicks.  Two sub-options:

- **(4a.i) Canvas-based** — `client.loft` opens a
  `lib/graphics::Canvas`, draws the 3×3 grid, polls click events.
  Clean, reuses lib/graphics infrastructure.  Probably needs
  graphics imports the wasm bundle doesn't currently include.
- **(4a.ii) DOM-direct via host imports** — extend
  `loft-rt.js` with a small DOM bridge: `dom_set_text(id, text)`,
  `dom_on_click(id, callback)`, etc.  Heavier infrastructure
  but matches what a real loft web app would want.

For v3.5 minimal, recommend **(4a.iii) status text only** —
`client.loft` connects to /ws, plays the game, prints
placements via `println` (which loft-rt.js routes to the host's
`log_write` → console).  The board rendering stays in the JS
shell (the same INDEX_HTML the JS-client v3 ships).
`client.loft` then has only the protocol logic, not the UI.

This is the smallest meaningful demo: "loft program runs in the
browser, talks to the server, plays the game."  Visual board
rendering is a follow-up.

**(4b) Handler architecture.**  client.loft uses the same
`web::ws_handler` + `pump` shape v2/v5 client programs already
use.  The pump callback receives messages, parses
`place:<mark>,<r>,<c>` / `gameover:<X|O|draw>`, calls
`host.dom_set_cell(r, c, mark)` (if 4a.ii) or `println` (if
4a.iii).  Writing this is straightforward once the WS bridge
works.

Effort: **S** for 4a.iii (status-text-only); **M** for 4a.i
(canvas) or 4a.ii (DOM bridge).

## Test strategy without a real browser

The cargo harness can drive `compile_and_run` from Node, not a
real browser.  `tests/wasm/host.mjs` already provides the Node
host shim (filesystem in memory, fake time, no DOM).  v3.5
extends it with the WS bridge bindings (using Node's `ws`
package or a hand-rolled raw-TCP WS handshake — same code as
loft-rt.js's browser bridge).

```
tests/multiplayer_v3_5.rs (sketch):
  1. Spawn tictactoe_server_v3.loft.
  2. Spawn `node tests/wasm/run_client.mjs <port>` — Node script
     that:
       - Loads pkg/loft.js
       - createHost() with WS bridge wired to Node's `ws` package
       - fetches client.loft from the server
       - calls compile_and_run([{main, fetched}])
       - exits 0 on "v3.5-probe: ok", non-zero otherwise
  3. Assert exit 0 + the expected stdout markers.
```

Reuses the tests/wasm/ infrastructure already in tree (per
plan-31's HTML export work).

## Out of scope (deferred to v4 or later)

- **Hot WASM swap** — that's v4's job, building on v3.5's
  bootstrap.
- **Per-client compile-on-server** — minimal v3.5 ships
  `client.loft` source verbatim; the interpreter compiles it on
  every page load.  Acceptable: client.loft is tiny and the
  interpreter is fast enough.
- **Canvas / DOM rendering from loft** — v3.5 minimal uses the
  HTML shell for visuals; loft handles only the protocol.  4a.i
  and 4a.ii are real follow-ups but not on the v3.5 critical
  path.
- **Multi-client (v2-style spectator routing) over WS** — keep
  v3 / v3.5 as single-client; the multi-client layer is its own
  v3.6 / v4 milestone.
- **TLS / wss://** — `ws://localhost` only.

## Risks

| Risk | Mitigation |
|---|---|
| The lib/web-in-wasm-pack question (Piece 2) is bigger than M | The spike (3.5.0) catches this in 30 min; if the answer is "needs full library-bundling rework", defer v3.5 and pivot to v4's per-program WASM compile path instead |
| `compile_and_run` has no streaming output mode — long-running clients can't `println` interactively | `compile_and_start` + `resume_frame` IS the streaming path (already shipped, used by playground); v3.5 client uses that instead.  Documented in 3.5.4 |
| WS message-buffer semantics on the JS side — backpressure when the inbox grows faster than `ws_recv` drains | Cap the inbox at 256 frames; drop oldest with a console warning.  Real production needs a different shape; v3.5 demo doesn't |
| The wasm interpreter doesn't support `parallel{}` (per [DESIGN_DECISIONS.md § C3](../../DESIGN_DECISIONS.md)) | client.loft's tic-tac-toe play is sequential; not affected.  Document the limit in the v3.5 README header |
